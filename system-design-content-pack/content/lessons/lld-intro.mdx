**Low-level design (LLD)** is the step where one box of an architecture becomes code you could write: the classes inside it, what each is responsible for, how they relate, and in what order they call one another for each use case. **High-level design (HLD)** decides which boxes exist and how data and traffic move between them; LLD opens one box and designs its insides.

## Boxes versus classes

The [interview playbook](/learn/playbook) and the [case-study template](/learn/case-study-method) stop where a food-delivery app has an order service, a payment service and a queue between them. An LLD question starts exactly there. Inside the order service, what is an `Order`? Who computes the total when a coupon is applied? What happens if the coupon expires while the user is paying?

| | High-level design | Low-level design |
| --- | --- | --- |
| Unit of design | Services, databases, queues, caches | Classes, interfaces, methods, objects |
| Main questions | Where does data live? How does it scale? What fails? | Who is responsible for what? How do objects collaborate? What is invalid? |
| Artefacts | Architecture diagram, API table, estimates | Class diagram, sequence diagram, code skeleton |
| Typical trade-off | Consistency against availability, cost against latency | Flexibility against indirection, reuse against coupling |

<Callout type="analogy" title="City map, then floor plan">

HLD is the city map: which districts exist and which roads join them. LLD is the floor plan of one building: which rooms there are, what each is for, and which doors connect them. Where the analogy stops: a floor plan is static, while LLD must also say who walks through which door in what order; a class diagram alone is never the whole answer.

</Callout>

## The workflow

Every LLD problem can be worked in the same order, and the order matters because each step narrows the next.

<Steps>

1. **Requirements.** What the system must do, must not do, and what you are assuming (one lot or many, prepaid or pay-on-exit). Say them out loud.
2. **Entities.** Underline the nouns: vehicle, spot, floor, ticket, payment. Each becomes a class, a field or nothing.
3. **Responsibilities.** One sentence per entity starting "knows" or "does": a `Spot` knows its size and whether it is free; a `ParkingLot` assigns spots and issues tickets. An "and" in the sentence hints at two classes hiding in one.
4. **Classes and relationships.** Turn responsibilities into fields and methods, then draw which objects own which, which merely use which, and how many of each (see [Class relationships and UML](/learn/class-relationships-uml)).
5. **Interactions.** Walk the main use case object by object (a vehicle arrives, the lot asks a floor for a spot, the spot is marked taken, a ticket is issued); a sequence diagram makes the gaps obvious.
6. **Edge cases.** Lot full, vehicle too large for any spot, lost ticket, payment fails, two cars arrive at the last spot at once. Each becomes a method, a state or a documented decision.
7. **Extensibility.** Name the change most likely to arrive next (electric-vehicle spots, hourly versus flat pricing) and show where it plugs in without rewriting what exists.

</Steps>

## What the interviewer is listening for

An LLD round is scored less on whether the code compiles than on the decisions you make visible along the way.

- **Clear responsibilities.** Every class can be described in one sentence, and none is called `Manager` or `Helper` because you could not say what it does.
- **Sensible relationships.** Ownership, usage and counts match the domain: a ticket refers to a spot; it does not own it.
- **Patterns used for a reason.** "Strategy here, because the spot-assignment rule is the thing most likely to change" earns credit; "Singleton" with no reason loses it. The pattern lessons, from [creational patterns](/learn/design-patterns-creational) on, teach the problem first.
- **Edge cases named.** Naming the full lot, the race for the last spot and the payment that times out shows you have run the system in your head.
- **Trade-offs said out loud.** More classes buy flexibility and cost indirection; a `switch` reads faster than four polymorphic classes until the fifth case arrives. Either is defensible if you name the cost.

<Callout type="interview" title="Narrate the step, not just the answer">

Say which step you are on: "I have the entities; before I draw classes I want one responsibility each." Interviewers can only credit reasoning they can hear, and narration lets them steer you early if the scope is off.

</Callout>

The foundation lessons build from the object up. [OOP pillars](/learn/oop-pillars) and [class relationships](/learn/class-relationships-uml) give you the vocabulary. Every case study follows one template (requirements, entities, class design, interfaces, interactions, patterns, edge cases, concurrency, extensibility), so learn it once and fourteen problems become one habit.
