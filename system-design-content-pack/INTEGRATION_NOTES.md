# Integration Notes for Claude Enterprise

Status: **final (Phase 7, 2026-11-22)**. This file tells the integrating instance exactly how to apply the pack to `sujalsoni26/box-by-box-system-design` without web access. Counts quoted here are the ones recorded in `CONTENT_STATUS.md` and `qa/METRICS.md` at the end of Phase 7; those two files are regenerated by the tools and win if they differ.

## 1. What the pack is

A drop-in superset of the repository's content and data layer plus three approved application changes. Paths under `content/`, `data/`, `types/`, `scripts/` and `components/` mirror the repository. Everything else (`*.md`, `plan/`, `research/`, `specs/`, `qa/`, `tools/`, `drafts/`) is documentation, tooling and provenance and is never copied.

## 2. Apply in one command

```bash
# from a checkout of the repository at or after commit e508232, after npm ci
/path/to/system-design-content-pack/tools/apply.sh /path/to/box-by-box-system-design
```

The script copies the five mirrored directories (adds and overwrites; deletes nothing) and runs `npm run check` (typecheck, lint, content validation). Pass `--no-check` to copy only. Manual equivalent: `rsync -a content/ data/ types/ scripts/ components/` into the checkout, then `npm run check` and `npm run build`.

If the repository has moved past `e508232`, diff `data/*.ts`, `data/glossary.json`, `types/curriculum.ts`, `scripts/validate-content.mjs` and `components/diagrams/interactive/recall-cards.tsx` before copying: the pack's versions are complete files generated from the `e508232` originals plus additions. To regenerate against newer originals, put them in `plan/base-data/` and run `python3 -I plan/merge_bundles.py`.

## 5. Verification steps

1. `npm run check` must print `OK: N lessons match N curriculum slugs … all compile.` (the pack's own run on a scratch checkout: see `qa/TECHNICAL_QA.md`).
2. `npm run build` must prerender every `/learn/[slug]` route; the pack was built on a scratch checkout at the end of Phase 7.
3. `node tools/mermaid-check.mjs <checkout> content/lessons` parses every Mermaid chart with the app's own `mermaid` package (needs `jsdom` installed in the checkout with `npm install --no-save jsdom`; it is not a project dependency). Expected: `0 failed`.
4. `npm run start -- -p 3111` and `node tools/render-check.mjs http://localhost:3111 content/lessons` renders every lesson page in headless Chrome through the DevTools protocol and confirms each chart produced an SVG. Charts inside a collapsed `<DeepDive>` render only when expanded, so a `pending` count on such a lesson is expected (today: `tcp-udp`). Needs Node 22+ and a Chrome binary, no npm packages.

Steps 1–4 are scripted: `tools/full-check.sh <scratch-checkout> [port]` runs the merge with `npm run check`, regenerates the documents and metrics, parses every chart, builds and serves the app and runs the render check, writing the outputs to `qa/render-check/`.

5. In a browser: open `/learn` and confirm modules 7–16 appear after module 6 with their stage labels; open one lesson per new module; open `/learn/class-relationships-uml` and confirm the class diagram and the sequence diagram render in both themes (evidence from the pack's own run: `qa/render-check/class-relationships-uml.png`); open `/learn/advanced-revision`, `/learn/case-study-method` and `/learn/lld-revision` and confirm the three new flashcard decks load; open `/practice` and confirm the existing decks and checks are unchanged.

## 6. Things that are specifications, not code

- `specs/simulations/*.md` describe nine simulations that do not exist. No lesson references them. Implementing one means adding the `.tsx` under `components/diagrams/interactive/`, registering it in `interactive-registry.tsx`, and then adding `<Interactive name="…" />` to the lesson named in the spec.
- `specs/diagrams/README.md` records that no new static diagrams are needed: every planned one became a Mermaid chart in its lesson or reuses a registered diagram.
- `recommendations/APP_CHANGES.md` lists the optional changes (`ConceptCard`, glossary links, a concept glossary, the practice-page deck listing, CI checks) that the content does **not** depend on.

## 7. Known limitations and open items

- All 101 planned lessons shipped, including the Wave C lessons (`distributed-sql`, `cloud-networking`, `multi-tenancy`, `cdc`, `brokers-compared`, `incident-response`) and the P2 case studies (`design-ticket-booking`, `design-payment-system`, `design-search-autocomplete`), so `plan/deferred-links-auto.md` lists no neutralised links. If a lesson is ever removed from a bundle set, re-run the merge: it drops the lesson from `data/curriculum.ts` and neutralises links to it automatically.
- `python3 -I plan/refresh_review_hashes.py --verify` reports any reviewed bundle edited after its review hash was recorded; it exits 0 on the delivered pack.
- The pack's `data/*.ts` files are complete files generated from the repository's originals plus additions. If the repository's data files changed after commit `e508232`, diff before copying (see §2).
- Mermaid renders client-side; the validator checks syntax shape, not rendering. `qa/TECHNICAL_QA.md` records the parse and render checks the pack ran and their results.
- In `next dev` (not in the production build) Next.js 16 logs a `Could not validate instant` prefetch error on lesson pages the first time they compile; it comes from the repository's `acronym.tsx` client reference under Turbopack's Cache Components mode, is unrelated to the pack's content, and does not occur in `next build`/`next start`.
