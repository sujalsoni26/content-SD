**Change data capture (CDC)** turns the database's own record of committed changes into a stream of events that other systems consume. [Write-ahead logging](/learn/wal) showed where that record lives and how logical decoding reads it; [Replication strategies in depth](/learn/replication-internals) showed Debezium creating a replication slot and writing one Kafka topic per table. This lesson is about the pattern around that machinery: why reading the log beats every other way of noticing a change, how to get an *application event* out reliably, and what the consumers of the stream must cope with.

## Three ways to notice a change

| Approach | How it works | What it misses or costs |
| --- | --- | --- |
| Polling a table | A connector re-queries each table for rows changed since its last poll (Confluent's JDBC source polls every 5 seconds by default) | Deletes vanish without trace, rows updated within the same timestamp or committed out of order can be skipped, and every poll is load on the table |
| Triggers | A trigger on each table copies every change into a changes table inside the same transaction | Every write now does two writes, every table needs its own trigger, and something still has to ship the changes table |
| Reading the log | The connector consumes committed changes from the transaction log in commit order, with the row's old and new values | Needs the logical WAL level and a slot that holds WAL until it is read, as the replication lesson warned |

Log-based capture is the only one of the three that sees every change, deletes included, in exactly the order the database committed them, without adding work to the transactions themselves. One setting decides how much of the old row you get: with PostgreSQL's default `REPLICA IDENTITY`, an update's *before* image holds only the primary key, and `REPLICA IDENTITY FULL` is needed for the previous values of every column.

## Dual writes lose events

The tempting design writes the row, then publishes an event from application code. It fails in the gap. If the process dies after the commit and before the publish, the order exists and no event ever says so, and no retry can know it was owed. If Kafka is unreachable, the application must choose between failing a request the database has already accepted and dropping the event. Across two services the same race produces events in a different order from the commits.

The **outbox pattern** closes the gap by making the event part of the transaction: the service inserts the row *and* an event row into an `outbox` table in the same commit, and CDC ships the outbox. Debezium's outbox event router, a Kafka Connect single message transform (SMT), reads an `aggregatetype` column to choose the topic (`outbox.event.Order` by default) and uses `aggregateid` as the message key, so every event about order 77 shares a partition and stays in order. Gunnar Morling described the pattern for Debezium in 2019; Chris Richardson's catalogue names the two ways to relay the outbox, polling it or tailing the log, and log tailing is the one this lesson is about.

## Snapshot, then stream

A new connector has history to catch up on. With Debezium's default `snapshot.mode = initial`, it opens the replication slot first, reads every existing row and emits each as a *read* event, then streams from the slot's position, so no change made during the snapshot is lost or doubled. A table added later, or a consumer that needs a rebuild, uses an **incremental snapshot**: a signal written to a signalling table makes the connector read the table in chunks of 1,024 rows by default, with watermarks that let it interleave chunks correctly with the live stream, the approach Netflix published as DBLog in 2020. The stream never stops while this happens.

## What an event looks like

Each record carries `before` and `after` row images, an `op` of `c`, `u`, `d` or `r` (the last for snapshot reads), `ts_ms`, and a `source` block with the database, table and log position. The key is the table's primary key and the topic is `prefix.schema.table`. After a delete, Debezium emits a **tombstone**, the same key with a null value (`tombstones.on.delete` is true by default), so that a compacted topic (see [Kafka](/learn/kafka-architecture)) can forget the row.

## At least once, in order per key

Debezium delivers **at least once**: after a crash it resumes from its last committed offset and replays what followed, so consumers see duplicates, never gaps. Order is guaranteed within a partition, and because the key is the primary key, all changes to one row arrive in commit order; changes to different rows, or different tables, carry no mutual order. The consumer's half of the bargain is the one from [Idempotency](/learn/idempotency): an upsert keyed by the primary key that applies the full `after` image is harmless to replay, and a consumer that stores the last `source` log position per key can skip anything older. [Delivery semantics](/learn/delivery-semantics) has the general argument.

## Schema evolution

`ALTER TABLE` happens, and the stream must survive it. The PostgreSQL connector reads the current column list from the decoding stream itself, so a new column appears in the next event without a restart; it emits no DDL events, because logical decoding does not carry them. The MySQL connector instead records every DDL statement in a schema history topic so that it can parse the binlog correctly after a restart. Consumers see the change as a changed record schema, and with Avro and a schema registry compatibility is checked at registration: Confluent's default mode is BACKWARD, which permits adding an optional field or deleting one and rejects a rename. The practical rules follow: add columns with defaults, never rename in place, and treat a type change as a new column plus a backfill.

One quiet failure belongs here. The slot advances only when the connector reads a change from a *captured* table; on a shared server where the captured database is quiet and another database is busy, WAL piles up on disk. Debezium's `heartbeat.interval.ms` (0, so off, by default) makes the connector report its position regularly, and `heartbeat.action.query` writes a dummy change so that there is always something to report.

## Where the stream goes

The same events feed a cache invalidator (delete the key and let the next read repopulate, as in [Caching](/learn/caching)), a search indexer that upserts documents, a warehouse loader and an audit log. A Flipkart-style price change becomes one `UPDATE` and, within a second, a cache miss, a fresh search result and a row in the analytics table, with no code in the catalogue service knowing about any of them.

<Callout type="analogy" title="The court stenographer">

Asking each witness afterwards what they said is polling: slow, incomplete, and the ones who have left the room (the deletes) say nothing. The stenographer's transcript is the log: every word in order, including the retracted ones. Where it breaks: a transcript is one document, while CDC fans the same transcript out to several readers who each keep their own place in it.

</Callout>

<Callout type="interview" title="Name the gap">

"I write the event to an outbox table in the same transaction as the row, and Debezium reads both from the WAL, so a committed change can never be missing its event. Delivery is at least once and ordered per key, so consumers upsert by primary key. The first run snapshots, then streams." The sentence about the gap between commit and publish is the one interviewers listen for.

</Callout>

<DeepDive title="Go deeper: why the outbox is safe but not free">

The outbox row is written once and read once by the connector, and nothing reads it afterwards, so the table must be pruned on a schedule or it grows without bound. It also means the event's shape is now schema in your database, versioned by migrations, which is exactly where you want it. What the outbox cannot do is make a *non-database* side effect atomic: an email or a payment call still needs an idempotency key and a consumer that tolerates replay.

</DeepDive>
