The server creates an order, the response is lost, the app retries, and now there are two orders (or a double charge). Retries and at-least-once queues make this common. An operation is **idempotent** if repeating it has the same effect as doing it once, like pressing a lift button five times.

GET, PUT and DELETE are idempotent; **POST is not**.

## The fix: an idempotency key

<Steps>

1. The client generates one unique ID per user action (a UUID such as `abc-123`) and sends it in an `Idempotency-Key` header. Every retry reuses it.
2. **New key:** process the request and save the key with its result, ideally in the same transaction.
3. **Seen key:** skip the work and return the saved result.
4. Keys expire after a while (for example, 24 hours). Stripe's payment API works this way.

</Steps>

```http
POST /payments
Idempotency-Key: abc-123
Content-Type: application/json

{"amount": 500, "currency": "INR"}
```

Making a chain of queues and consumers behave as if each message were handled once is [Delivery semantics and exactly-once](/learn/delivery-semantics); undoing earlier steps when a later one fails is [Sagas and compensating actions](/learn/sagas).

<Callout type="warning" title="Not the same as double booking">

Two *different* users grabbing one seat is a **concurrency** problem, solved with row locks (`SELECT … FOR UPDATE`), a unique constraint on `(show_id, seat_id)`, optimistic locking (version numbers) or temporary holds. Idempotency handles the *same* request repeated; concurrency control handles *different* requests competing.

</Callout>

<DeepDive title="Go deeper: the edge cases">

- **Same key, different body.** Store a hash of the request with the key. If a retry arrives with the same key but different parameters, reject it; Stripe returns an error in this case.
- **Same key while the first is still running.** Two copies can arrive at once. Insert the key first under a unique constraint, so the second copy fails to claim it and can wait or get a 409 Conflict.
- **Atomicity.** Saving the key and doing the side effect must succeed or fail together; otherwise a crash between them either repeats the charge or loses it.

</DeepDive>
