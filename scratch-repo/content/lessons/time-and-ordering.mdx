Every machine has a clock, and no two agree. A **logical clock** orders events by the messages that connect them rather than by the time of day, the only ordering that machines sharing nothing but a network can trust (see [What makes a system distributed](/learn/distributed-fundamentals)).

## Two clocks on every machine

Your operating system offers two clocks.

|  | Wall clock | Monotonic clock |
| --- | --- | --- |
| Answers | "What time is it?" (seconds since 1970) | "How much time has passed?" |
| Linux, Java | `CLOCK_REALTIME`, `System.currentTimeMillis()` | `CLOCK_MONOTONIC`, `System.nanoTime()` |
| Can it jump? | Yes: NTP steps it, an operator resets it, a leap second repeats a second | No: it only moves forward, from an arbitrary origin |
| Comparable across machines? | Roughly, within the NTP error | Never; the number means nothing off the machine |
| Use it for | Timestamps people read, expiry dates | Timeouts, durations, rate limits |

NTP corrects wall clocks, typically to within milliseconds or tens of milliseconds over the internet and around a millisecond on a quiet local network. Between corrections a quartz oscillator drifts with temperature; Spanner's designers budget 200 microseconds per second as a worst case, about 17 seconds a day uncorrected. The correction itself can step the clock, backwards included, so a duration computed from two wall-clock readings can come out negative.

Then there are **process pauses**. A stop-the-world garbage collection or a live VM migration freezes your code for milliseconds to, in bad cases, minutes, while every clock keeps running. The code resumes with a stale idea of "now" and no sign it was gone, which is what breaks leases (see [Leader election](/learn/leader-election)).

<Callout type="warning" title="Cloudflare and the leap second">

On 1 January 2017 a leap second made wall clocks repeat a second. Cloudflare's DNS software measured upstream round-trip times with Go's `time.Now()`, which then read the wall clock, so one measurement came out negative and a random-number call that rejects negative arguments panicked; at the peak about 0.2% of DNS queries failed. Go 1.9 later gave every `Time` value a monotonic reading so that subtracting two of them is safe. Measure durations with the monotonic clock, always.

</Callout>

## Why last-write-wins loses data

When two replicas accept writes to the same key, something has to pick a winner. **Last-write-wins (LWW)** keeps the write with the highest wall-clock timestamp; Cassandra works this way, with the timestamp supplied by the client or the coordinator's clock.

Suppose node A's clock runs 40 ms ahead of node B's. A customer changes their delivery address through A, then corrects it 10 ms later through B. A stamps the first write `t + 40`, B the second `t + 10`, and LWW keeps the *first* address. The correction is gone, no error is raised, and until someone notices, the fast clock wins every conflict. [Quorums](/learn/quorums) shows the alternative.

## Happens-before

In 1978 Lamport replaced "earlier" with something observable. Event a **happens before** event b if both are in the same process and a came first, if a sends a message that b receives, or if a chain of such steps connects them. Otherwise they are **concurrent**: no information flowed between them, so nobody can say which was "really" first.

## Lamport clocks

A **Lamport clock** is one counter per node: increment it before every local event, stamp every message with it, and on receipt set it to the larger of its own value and the message's timestamp, plus one. The guarantee is one-directional: if a happens before b then L(a) is less than L(b).

A's write (1) happens before B's write (3), and the numbers agree. But C's write (1) is also smaller than B's write (3), and nothing from C reached B before B wrote: the two are concurrent. <mark>A smaller Lamport timestamp never proves that an event came first.</mark> Breaking ties by node id gives a total order, but an invented one, not a discovered one.

## Vector clocks

A **vector clock** keeps one counter per node on every node. Increment your own entry before an event, send the whole vector with each message, and on receipt take the element-wise maximum, then increment your own entry. If no entry of V(a) exceeds the matching entry of V(b) and at least one is smaller, a happens before b; if each vector is larger somewhere, the events are concurrent.

| Event (same run as above) | Vector [A, B, C] | Against A's write [1, 0, 0] |
| --- | --- | --- |
| A writes | [1, 0, 0] | — |
| C writes | [0, 0, 1] | Each larger somewhere: **concurrent**, a real conflict |
| B receives m1 | [1, 1, 0] | Dominates: happened after |
| B writes | [1, 2, 0] | Dominates: happened after |

Detecting concurrency is what a Lamport clock cannot do, and it is why Dynamo-style stores keep a vector of (node, counter) pairs with every version of a value. The price is metadata that grows with the number of writers.

## Hybrid logical clocks

A **hybrid logical clock (HLC)** pairs the highest physical time a node has seen with a logical counter that only moves when the physical part does not. It orders events like a Lamport clock, stays close to the wall clock, and fits in 64 bits. CockroachDB timestamps transactions with HLCs and crashes a node whose clock drifts from at least half the others by 80% of the configured maximum offset: a wrong clock is worse than a missing node.

## TrueTime: paying for a bounded error

Google's Spanner takes the opposite route: make physical time trustworthy by measuring its error. **TrueTime** returns an interval, `TT.now()` giving `[earliest, latest]`, guaranteed to contain the true time; half its width is the uncertainty ε. GPS receivers and atomic clocks in each data centre keep ε small: in the 2012 paper it moved between about 1 and 7 ms, about 4 ms most of the time, and generally below 10 ms.

**Commit wait** turns that bound into ordering. A transaction's leader picks a commit timestamp s no earlier than `TT.now().latest`, then holds the result back until `TT.after(s)` is true, so s is definitely in the past; the expected wait is about 2ε. In exchange, if T1 commits before T2 starts anywhere on Earth, T1 gets the smaller timestamp: globally ordered transactions and lock-free reads at any past timestamp (see [Linearizability](/learn/linearizability)). The costs are the clock hardware, the wait on every commit, and a system that slows down whenever ε grows.

<Callout type="analogy" title="Numbered letters, not postmarks">

Two friends write to each other, but their local post offices stamp dates wrongly. Instead of trusting postmarks, each numbers their letters and writes "the last letter I received from you was number 7" at the top. Anyone reading the pile can reconstruct who knew what when they wrote. That is a Lamport clock. Where it falls short: a number tells you what the writer had seen, not whether two letters were written in ignorance of each other; for that you need a count per writer, which is the vector clock.

</Callout>

<Callout type="interview" title="Say how you order events">

"I never order writes across machines by wall clock. Inside one partition a single leader assigns the order; across replicas I attach version vectors so concurrent writes are detected instead of dropped; and if the product needs real-time ordering, I need bounded clock uncertainty and must wait it out, which is what Spanner's commit wait does."

</Callout>

<DeepDive title="Go deeper: where TrueTime's uncertainty comes from">

Each data centre has time masters: most carry GPS receivers, and a few "Armageddon masters" carry atomic clocks, because the two fail in different ways. A daemon on every server polls masters every 30 seconds and, between polls, widens its uncertainty at the assumed drift rate of 200 microseconds per second. That is why ε is a sawtooth: it is smallest just after a poll and about 6 ms wider just before the next one, with master uncertainty and network delay added on top. When the uncertainty is larger, Spanner does not become incorrect; it waits longer.

</DeepDive>
